# 첫 제품 요구사항 초안

상태: 기술 조사에 사용할 가정. 실제 대상 사용자에게 확인하지 않았으며 제품 요구사항 확정을 뜻하지 않는다.
첫 앱 후보는 정수 단위의 수량·비용 정책 계산기다. 실거래·세금·결제 처리는 포함하지 않는다.

## 사용자와 작업 가정

정책을 자주 바꾸는 담당자가 계산 구현을 작성하지 않고, `.ax` 조건을 수정해 결과를 확인한다. 단위는 소수점 없는 가상 비용 단위다. 숫자 범위를 제한해 u32 wrapping과 업무상 일반 정수 계산이 일치하도록 한다. 이 범위와 네 항목 제한이 실제 업무에 맞는지는 사용자 확인이 필요하다.

| ID | 작업 | 입력과 유효 범위 | 결과 조건 |
| --- | --- | --- | --- |
| T1 | 기본 금액 계산 | 단가 0~10,000, 수량 0~100 | 결과는 두 값의 곱, 최대 1,000,000 |
| T2 | 상한 정책 적용 | 기본 금액·상한 각각 0~1,000,000 | 결과는 두 값 이하이며 그중 하나다. 구현 방법은 지정하지 않는다. |
| T3 | 네 항목 집계 후 정책 적용 | 항목별 금액 0~250,000, 상한 0~1,000,000 | 네 항목 합계를 T2 정책에 전달한다. 빈 항목은 0이다. |
| C1 | 최소 비용 정책으로 변경 | 금액·하한·상한 0~1,000,000, 하한 ≤ 상한 | 구간 안의 금액은 유지하고 아래는 하한, 위는 상한을 반환한다. 하한은 기본 금액보다 클 수 있다. |
| U1 | 부족한 정책 보완 | T2와 동일 | 상한 이하 조건만으로는 할인 정책이 정해지지 않음을 확인하고, 결과가 두 입력 중 하나라는 조건을 추가한다. |

T1과 T3는 작성한 관계식의 합성·실행을 확인하는 보조 사례다. 합성의 차별성을 판정할 핵심은 T2와 C1이다. T2의 값 선택과 C1의 구간별 구현은 AMI·함수 본문·JavaScript 알고리즘으로 제공하지 않는다. U1에서 가능한 결과를 보여주고 사용자에게 의도를 확인한다. T2와 C1이 원하는 정책이라는 사용자 확인 없이는 기술적으로 증명돼도 제품 요구를 충족했다고 하지 않는다.

## 사전에 고정한 기대 결과

[테스트 기대값](../../tests/fixtures/first-product/expected.json)은 합성 실행 전에 작성했다. 입력별 결과를 명시적으로 기록했으며 생성 코드에서 역으로 추출하지 않는다.

- T1: (0,100)→0, (1,1)→1, (25,4)→100, (10,000,100)→1,000,000.
- T2: (0,80)→0, (100,80)→80, (40,80)→40, (80,80)→80, (1,000,000,0)→0.
- T3: (0,0,0,0)→0, (10,20,30,40)→100, (250,000,250,000,250,000,250,000)→1,000,000. 집계 후 T2로 상한을 적용한다.
- C1: (0,20,80)→20, (40,20,80)→40, (100,20,80)→80, (20,20,80)→20, (80,20,80)→80, (99,50,50)→50.
- U1: (100,80)에서는 0과 80이 모두 허용된다. 이는 동일 입력의 대안 결과 예시이며 전체 입력의 자동 모호성 검사를 구현했다는 뜻은 아니다.

## 오류·변경 수락 조건

입력 범위 초과와 하한 > 상한은 runtime 진입 전에 거부한다. 모순된 전제조건과 불가능한 후조건은 새 WASM을생성하지 않는다. 전제조건의 존재 확인과 후보 증명은 구분해 기록한다.

정책 변경에서는 T2 명세를 C1 명세로 바꿔 새 후보를 합성한다. 이번 조사는 개별 후보 생성까지 확인하며, 실제 앱에서 변경·저장·last-good 결과를 연결하는 것은 별도 구현과 브라우저 검증이 필요하다.

## 첫 앱에 필요한 것

입력·기본 금액·집계·최종 정책 결과를 한 화면에서 사용하고 필요한 입력 상태를 저장한다. 계산은 생성된 WASM에 연결한다. `.ax` 작성과 조건 보완 안내, 오류 위치, 어떤 명세에서 결과가 생성됐는지 표시, 실패 후 복구가 필요하다. 기존 웹 runtime 재사용 가능성은 조사하되 이번에 새 UI는 만들지 않는다.

## 실제 사용자 확인이 필요한 결정

- 이 세 작업과 상한→최소 비용 변경이 실제로 필요한가?
- 정수 단위, 네 항목, 입력 범위가 업무에 충분한가?
- 상한 정책과 최소 비용 정책에서 기대한 결과가 맞는가?
- 일반 코드·스프레드시트 방식보다 조건 작성과 증명이 유용한가?

이 확인이 남아 있으므로 수요, 명세 작성 성공, 제품 완주와 기존 코드 대비 효과는 아직 미검증이다.
