# v5.0 Application Boundary Baseline

v5.0 separates pure scalar proof from application data and host effects. It
does not add a new contract semantics or change the frozen v4 behavior.

## Responsibilities

### Verified Core

The verified core is the deterministic scalar computation represented by a
contract and its candidate. v4 supports `u32`, `i32`, and `bool`, contract
preconditions and postconditions, synthesis, Z3 proof, and WASM execution.
Only a candidate whose proof result is `VERIFIED` is wrapped as a
`VerifiedComputation` and emitted for the application call path.

### Application Runtime

`axiom-application` owns `ApplicationValue`, `ApplicationCall`, and the
application-side failure types. `ApplicationValue` can represent integers,
booleans, text, lists, and records, but only the v4 scalar types can cross into
the core. Text, lists, and records are retained as application data and are
rejected by scalar lowering.

The `app-run` CLI command is the v5.0 executable vertical slice:

```sh
cargo run -p axiom-cli -- app-run tests/legacy/basics/mul8.ax -- 5
```

It parses the contract, builds and proves the candidate, validates the
application input, lowers it to the WASM ABI, checks `requires`, executes the
WASM export, and lifts the result back to `ApplicationValue`. The integration
test exercises this command and checks that `mul8(5)` returns `Integer(40)`.

### Effect Boundary

`EffectRequest` represents a request to the outer host. It is not a core value,
and `BoundaryOperation::Effect` is distinct from
`BoundaryOperation::Application`. v5.0 has no HTTP, storage, clock, browser, or
other host adapter; dispatch without an adapter returns `EffectFailure`.
External values must be decoded and schema-validated by their host adapter
before they are passed to `ApplicationCall`. `VerifiedComputation` rejects
`extern` declarations so an external implementation cannot execute as part of
a pure core call.

## Dependency Direction

```text
axiom-cli → axiom-application → axiom-parser / axiom-synth / axiom-verify / axiom-wasm
                                      axiom-synth → axiom-ami / axiom-verify / axiom-wasm
```

No core crate depends on `axiom-application` or a browser, HTTP, or storage
implementation. The parser contains syntax-level AST types for the broader
language, but the scalar verifier rejects types it does not implement. The
browser host generated by `axiom-cli/src/web.rs` owns DOM updates, fetch,
`localStorage`, and rendering; those operations do not enter the proof core.

## Value Contract

| Boundary value | Verified core type | Rule |
| --- | --- | --- |
| `ApplicationValue::Integer` | `u32` | Accept only values in `0..=u32::MAX`. |
| `ApplicationValue::Integer` | `i32` | Accept only values in `i32::MIN..=i32::MAX`; preserve the two's-complement bit pattern. |
| `ApplicationValue::Boolean` | `bool` | Accept only a boolean value; integer `0` and `1` are not coerced. |
| `Text`, `List`, `Record` | none in v5.0 | Reject as unsupported core input types. |

Core outputs are lifted using the declared result type: `u32` and `i32` become
application integers, and boolean output accepts only the ABI values `0` or
`1`. No text, record, or list conversion is implied.

The command-line token parser maps `true` and `false` to booleans, integer
tokens to integers, and other tokens to text. It does not infer a contract type
and then coerce the token to match it; `ApplicationCall` performs exact type
and range validation before WASM execution.

## Trust and Failure Boundaries

The proof establishes the candidate's pure behavior under the frozen v4
semantics. It does not prove the solver, WASM engine, or host runtime correct;
v4.8 backend conformance supplies execution evidence for supported cases. It
also does not establish that an HTTP response is truthful, browser APIs are
correct, `localStorage` persists data, DOM rendering is correct, or an external
implementation follows its declared contract. Such data must be validated at
the host boundary before it is lowered to a scalar input.

Compilation/proof failures remain `CompileError` values and preserve the v4
`ContractCheck`, `SynthesisResult`, and `ProofResult` states. Application input
validation uses `BoundaryError`; rejected preconditions, WASM runtime failures,
output-lifting failures, and adapter failures use `BoundaryFailure`. These
application failures are not reported as proof counterexamples.

## v5.1 Thin Web Runtime

Generated `app.js` instantiates `app.wasm` and calls only its verified exports.
`window.synthetix.call(name, args)` and page actions check argument count and
`u32`/`i32`/`bool` types before lowering values to the WASM ABI, then lift the
result by the declared return type. Required preconditions run through a
generated WASM predicate export using the same scalar lowering as the verified
contract. Top-level page inputs accept `text`,
`number` (`u32`), `i32`, or `bool`; nested inputs and application collections
remain unsupported by this bridge. A page state is updated from the WASM result
and the DOM is rendered again.

The outer host can register one `window.synthetix.registerEffectAdapter`
callback and submit `{ name, inputs }` through
`window.synthetix.requestEffect(request, statePath)`. The adapter result may be
written to application state and rendered. It does not enter WASM or become a
proof assumption. Missing adapters, rejected requests, invalid inputs, and
runtime traps are surfaced as `APPLICATION_RUNTIME_ERROR` with the source file;
contract calls also include the contract name. They do not use `ProofResult`
states.

The generated runtime evaluates page/UI expressions for display and state
initialization. It does not translate contract bodies into JavaScript. The
v5.1 integration test builds an actual project, instantiates its generated WASM
in Node.js, drives numeric and boolean inputs through state and contract calls,
checks rendered values, and exercises successful and failing effect adapters.

## v5.2 State Transitions

A reducer button stages ordered updates against a clone of current application
state. Each later update reads earlier staged values. The runtime commits the
new state only after every verified WASM call succeeds, and exposes the
`APPLIED` or `FAILED` transition result through `window.synthetix.lastTransition`.
A failed update preserves the original state and reports
`APPLICATION_TRANSITION_FAILURE` with its event, update index, source, and
application cause.

## v5.3 Application Data

`ApplicationValue` represents integer, boolean, text, list, and record data and
uses a tagged JSON form for serialization. `list_item` and `record_field` make
extraction explicit; `verified_scalar` accepts only integer or boolean values.
`ApplicationCall` then checks the extracted scalar against the contract's
declared type and range before lowering it to WASM. Scalar results are lifted
back into `ApplicationValue`. Text, lists, and records are never passed to the
verified core as collections.

The v3 Todo project keeps its text draft and list of record values in
application state. Its `done` field is explicitly supplied as a boolean to the
verified `toggle` contract, and the WASM result updates the record and rendered
list. Serialization round-trip and malformed JSON are checked separately from
contract verification.

## v5.4 Persistence Boundary

Only states declared with `persist` enter the storage envelope; all other
states start from their declared initial values. `storage_schema_version` in
`synthetix.toml` defaults to `1` and is stored with the persisted values. The
runtime validates the envelope and top-level declared state types before
restoring them. It reads the older per-state v3.1 keys once and rewrites them
into the versioned envelope.

The browser runtime uses `localStorage` through a small get/set adapter. A host
may provide `window.synthetixStorageAdapter` with `getItem` and `setItem`. A
schema migration receives `{ page, fromVersion, toVersion, values }` and must
return the migrated persisted values. Hosts can set
`window.synthetixStorageMigration` before the bundle loads, or register a
migration through `window.synthetix.registerStorageMigration` and call
`window.synthetix.restore()`. Corrupt data, incompatible versions without a
migration, invalid migrated values, and storage failures are reported as
application runtime errors; they never become proof counterexamples.

## v5.5 Typed External Adapter

Imported `extern` declarations are emitted as runtime signature metadata and
are excluded from verified exports and `app.wasm`. `window.synthetix.requestExtern`
checks arguments against the declaration, sends `{ name, source, inputs,
responseType }` to the registered effect adapter, validates the response type,
and may store the result in a matching scalar application state. General effect
responses must be JSON-compatible application values; unsupported values are
rejected.

`window.synthetix.lastEffect` reports `LOADING`, `SUCCEEDED`, or `ERROR` while
the adapter runs. Adapter/network and response validation errors include the
extern source and remain application runtime errors. A returned value stays
application data; a caller must explicitly pass supported scalar data to a
verified contract when it needs a verified computation. This does not prove the
external service's factual correctness.

## v5.6 Async Effects

An effect adapter receives `(request, { signal, requestId })`. A newer request
for the same target state supersedes the earlier request; the earlier signal is
aborted and its eventual response cannot update state or replace the current
effect status. `cancelEffect(targetStateOrName)` cancels matching pending work,
and `cancelEffect()` cancels all pending work. A cancelled request resolves to
`undefined`. `retryEffect(targetStateOrName)` repeats a failed request using its
saved inputs. Requests for separate targets can complete independently, so one
failed adapter does not discard another target's successful update.

`lastEffect` adds a request id and target state and reports `CANCELLED` alongside
`LOADING`, `SUCCEEDED`, and `ERROR`. Adapter failures remain application runtime
errors. The generated-runtime test covers late stale responses, explicit cancel,
retry after a transient failure, and partial success/failure with real generated
WASM.

## v5.7 Web Integration

The Node integration tests instantiate generated `app.wasm` through generated
`app.js`, compare scalar calls with the reference evaluator and Z3 point proofs,
and check the rendered state, invalid input, extern/API errors, storage failures,
and source locations. A dev-project test changes a real source file through
valid, invalid, and recovered builds, then reads the version, source error, and
generated bundle through the HTTP routes. The runtime polling callback is
executed to verify reload on version change and removal of a recovered error.
The same server test checks `app.proof.json` maps a verified contract to its
project-relative source file.

## v5.8 Static Packaging

`axiom build` emits a self-contained static directory, including `app.config.js`
for public deployment settings. The Node integration test compares all generated
files across two builds and executes the bundle with a staging configuration;
the effect adapter reads the configured API base URL through
`window.synthetix.config`. `examples/web-counter` is the starter project. The
VSCode package is rebuilt with the current CLI and checked for source/package
hash equality plus extension activation smoke.

## v5.9 Release Path

The `v5_release_path_keeps_proof_wasm_state_effect_and_static_config_together`
integration test launches the CLI to check and build a project, inspects the
proof manifest and static files, then runs the generated runtime against its
WASM. It verifies that a page action and explicit verified call use the contract
export, while a typed extern request updates application state through the host
adapter and deployment config. The updated persisted state is checked in its
versioned envelope, then restored and rendered. The extern implementation stays
outside the verified contract list and WASM; v6.8 records its trust boundary
separately.

## v6.8 FFI Trust Boundary

The web proof artifact uses schema version 4. Proof status lives under
`verification` with scope `WASM_CONTRACTS_ONLY`; its `contracts` entries describe
only verified WASM candidates. `external_boundaries` separately records each
`extern` declaration's source, input/output types, `HOST_EFFECT` marker,
`UNVERIFIED` implementation status, and `EXTERNAL_IMPLEMENTATION` boundary.
`verification_scope` states that host implementations are unverified and that
runtime response validation checks the declared scalar type only.

Each external entry records that a host adapter must be registered when called
and that Axiom does not prove the external behavior matches application intent.
`audit_metadata.status` is currently `NOT_PROVIDED`; the build has no input for
caller-supplied audit data. The generated runtime passes the effect and trust-boundary
markers to the adapter. Missing adapters, invalid arguments or responses, and
adapter errors remain application runtime failures; they are never proof
counterexamples. A type-valid external result is still unverified application
data, not a proof of its factual correctness.

## v5.0 Scope

This baseline does not implement full records, lists, strings, state
management, reducers, async execution, HTTP, storage, a renderer, effect
inference, or a capability system. It defines the boundary and provides one
executable scalar call through verified WASM. Later milestones can add host
adapters without moving their behavior into the verified core.
