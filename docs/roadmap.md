# Synthetix 완성을 위한 로드맵

상태: 첫 제품의 기준 로드맵으로 고정. 이후에는 기능이나 단계를 추가하지 않고, 아래 착수 작업의 근거와 실행 결과를 별도 문서에 기록한다. 범위 변경이 필요하면 변경 이유와 완료 기준의 영향을 명시한다.

## 완성의 정의

사용자가 입력·출력과 반드시 성립해야 하는 조건을 `.ax` 명세로 작성하면, Synthetix가 조건을 만족하는 구현을 합성하고 증명해 실행 가능한 프로그램으로 만든다. 사용자는 핵심 계산 로직을 직접 구현하지 않고도 실제 문제를 해결하고, 조건을 바꿔 프로그램을 수정할 수 있다.

첫 제품의 완성은 아래 흐름을 프로젝트 내부 개발자의 도움 없이 끝낼 수 있는 상태다.

> 문제 정의 → 명세 작성 → 합성·증명 → 앱 실행 → 요구사항 변경 → 다시 사용

이 문서는 기존 버전별 계획과 독립적으로 작성한 새 제품 로드맵이다. 이전 SPEC과 측정 기록은 기존 기능의 근거로 남기되, 새 작업의 우선순위와 완료 기준을 대신하지 않는다. 아래 내용은 제안이며 완료 보고가 아니다.

## 첫 제품의 범위

첫 대상으로 **규칙 기반 수량·비용 계산기**를 제안한다. 한도, 구간별 규칙, 최소·최대값, 유효 입력 조건이 있고 결과를 사람이 따로 계산해 확인할 수 있는 작은 업무 도구다. 실제 사용자 문제를 조사한 결과는 아니므로 첫 단계에서 채택 여부를 결정한다.

예상 사용자 작업은 다음 세 가지다.

| 작업 | 사용자가 명세에 적을 내용 | 앱에서 확인할 결과 |
| --- | --- | --- |
| 기본 계산 | 수량·단가의 허용 범위, 결과가 만족할 관계 | 입력과 계산 결과, 범위 밖 입력 설명 |
| 조건별 정책 | 특정 조건에서 적용할 규칙, 결과의 하한·상한 | 조건에 따른 결과와 경계값 처리 |
| 항목 집계 | 제한된 항목 수, 각 값의 범위, 집계 관계 | 여러 항목의 합계와 정책 적용 결과 |

세 작업은 한 앱에서 이어져야 한다. 고립된 함수 예제 세 개를 만드는 것으로 완료하지 않는다. 항목 수와 숫자 범위는 현재 증명 모델 안에서 명시적으로 제한하고, 정수의 단위와 overflow 처리도 명세의 일부로 정한다.

명세에 결과의 관계를 쓰는 것은 허용한다. 개발자가 AMI 후보, `fn` 구현, JavaScript 계산 함수 또는 문제별 숨은 정답을 넣어 합성을 대신하면 제품 검증에서 실패다. 화면·입력·상태는 선언하거나 공통 runtime을 사용하되, 같은 핵심 계산을 화면 코드에 중복 구현하지 않는다.

첫 제품은 아래 네 가지를 함께 입증해야 한다.

- 사용자가 핵심 계산 알고리즘을 작성하지 않는다.
- 구현 방법을 지정하지 않은 조건에서 시스템이 후보 구현을 탐색한다.
- 선택한 후보가 선언한 모든 유효 입력에서 조건을 만족함을 증명한다.
- 정책 변경 후에도 구현을 직접 고치지 않고 새 후보를 합성·증명한다.

세 작업 중 적어도 하나는 구현식이나 정답 템플릿이 주어지지 않은 관계·제약 중심 문제로 정한다. 단순 계산식의 변환이나 고정 템플릿 선택만 성공하면 앱 동작은 확인할 수 있지만 합성의 가치는 입증하지 못한 것으로 기록한다. 실제 엔진이 이 기준을 만족하는지는 가능성 조사에서 확인한다.

동일한 정책 변경을 기존 코드로 처리할 때와 명세로 처리할 때의 작성·수정 작업, 소요 시간, 오류와 도움 요청을 비교한다. 같은 요구와 환경에서 관찰한 결과만 남기며, 규모가 작은 계산기에서 항상 더 빠르다고 가정하지 않는다. 사용자가 조건의 증명이나 정책 변경에서 얻는 이점을 설명할 수 없다면 첫 대상의 적합성을 다시 검토한다.

자연어 요구사항을 자동으로 정확한 명세로 바꾸는 기능은 첫 완성의 필수 조건이 아니다. 우선 사람이 이해하고 작성할 수 있는 `.ax` 명세와 작성 안내를 제공한다. 생성된 구현의 증명은 명세에 대한 증명이며, 명세가 사용자의 의도와 일치한다는 보장은 별도로 확인한다.

## 현재 출발점

저장소에는 parser/type checker, 제한된 후보 합성, Z3 검증, WASM 출력, 프로젝트 연결과 증분 검증, 웹 입력·상태·저장·effect runtime이 있다. 내부 예제와 회귀 검증도 존재한다.

현재 확인된 것은 엔진과 내부 예제의 동작이다. 외부 사용자가 실제 업무 요구를 명세로 옮기고 앱을 끝까지 만드는지는 아직 입증되지 않았다. 새로운 엔진을 처음부터 만들기보다, 이 흐름에서 실제로 막히는 부분을 찾아 해결한다.

기존 동작과 검증 경계의 근거: [예제](../examples/README.md), [application boundary](application-boundary.md), [의미론](semantics.md).

## 진행 단계

### 1. 실제로 해결할 문제를 고정한다

**목표:** 어떤 사람이 어떤 작업에 Synthetix를 사용할지 정한다.

- 대상 사용자 한 명 이상에게 현재 계산 과정, 입력, 출력, 예외 상황과 변경 사례를 확인한다.
- 위 계산기 제안이 맞는지 검토하고, 실제 문제가 다르면 이 단계에서 대상으로 교체한다.
- 정상 입력, 경계 입력, 거부할 입력, 요구사항 변경을 포함한 사용자 작업 세 개를 고정한다.
- 사용자가 검토한 입출력 예시와 기대 결과를 먼저 기록한다. 생성된 프로그램에서 기대 결과를 역으로 만들지 않는다.
- 엔진 범위 밖인 요구와 host에 맡길 화면·저장 기능을 명시한다.

**완료 기준:** 사용자가 “이 결과라면 내 작업에 쓸 수 있다”고 확인한 문제 설명, 세 작업의 성공 조건, 독립적인 기대 결과가 있다. 실제 사용자 확인 전에는 제품 수요를 입증했다고 주장하지 않는다.

**결과물:** 제품 요구 문서, 사용자 작업 목록, 수락 검증 데이터.

### 2. 사용자가 명세를 작성할 수 있게 한다

**목표:** 개발자가 대신 써주지 않아도 요구를 올바른 `.ax`로 표현한다.

- 하나의 작성 흐름으로 입력 타입·범위 → 결과 조건 → 예시 확인을 안내한다.
- 공식 문법과 현재 지원 범위를 좁고 일관되게 보여준다. 여러 문법을 동시에 배워야 하는 흐름을 피한다.
- 문법·타입·조건 오류를 source 위치와 수정 가능한 설명으로 전달한다.
- 예상 결과와 명세가 충돌하는지 확인하는 흐름을 제공한다. 예시 통과와 전체 조건 증명을 구분한다.
- 모순된 조건과 여러 정답을 허용하는 조건을 구분한다. 여러 구현이 조건을 만족해도 사용자 요구가 충족되면 성공이다.

명세가 부족한 경우도 별도의 사용자 작업으로 검증한다. 예를 들어 “결과는 0 이상, 총액 이하, 최소 금액 이상”만으로는 기대한 할인율이나 적용 구간을 정하지 못한다. 서로 다른 두 결과가 같은 입력에서 조건을 만족하는 사례를 보여주고, 사용자가 빠진 정책을 찾아 조건을 보완하도록 한다. 같은 입력에서 다른 결과가 가능하다는 증거와 서로 다른 구현이 존재한다는 사실은 구분한다.

의도한 정책에 따라 결과가 하나로 정해져야 한다면 보완 후 결과의 유일성을 확인한다. 여러 결과를 의도적으로 허용한다면 허용 범위와 선택 기준을 사용자에게 확인받고 기록한다. 예시 몇 개의 일치는 명세 전체의 충분함을 입증하지 않는다. 자동으로 대안 결과를 찾거나 유일성을 검사하는 기능의 구현 필요성은 가능성 조사에서 결정하며, 현재 지원한다고 가정하지 않는다.

**완료 기준:** 내부 구현을 모르는 참여자가 문서로 세 작업의 명세를 작성하고, 의도적으로 잘못된 조건 하나와 조건이 부족한 사례 하나를 찾아 보완한다. 보완 전후의 허용 결과와 사용자 의도 확인을 기록한다. 관찰자가 명세나 정답을 대신 작성하면 해당 시도는 통과로 세지 않는다.

**결과물:** 명세 작성 가이드, 작성 예제, 오류 설명과 사용자 관찰 기록.

### 3. 실제 명세를 합성·증명한다

**목표:** 선정한 문제를 구현 코드 없이 해결한다.

- 세 작업의 명세를 현재 합성기로 실행해 표현 불가, 후보 탐색 실패, 증명 실패를 따로 기록한다.
- 실패한 사용자 작업은 아래 엔진 확장 판단 기준으로 조사하고, 채택한 부족 기능만 추가한다. 이미 지원하는 기능과 패턴은 재사용한다.
- 핵심 정책에는 결과 조건만 쓰는 사례를 포함한다. 구현식을 옮겨 적은 예제만으로 합성의 유용성을 판단하지 않는다.
- 증명 전에 전제조건을 만족하는 유효 입력이 실제로 존재하는지 확인한다. 유효 입력이 없는 명세에서 후조건의 함의가 공허하게 참이 되는 경우는 정상적인 합성 성공으로 처리하지 않는다. 존재 여부를 확인하지 못한 경우도 성공으로 처리하지 않는다.
- 합성한 후보가 모든 유효 입력에서 소스 수준의 조건을 만족하는지 증명한다. 생성 WASM의 의미 보존 검증은 이 증명과 별도로 수행한다. 컴파일러의 의미 보존을 형식적으로 증명하지 않았다면 경계값·대표 입력·reference/AMI/WASM 차등 테스트로 확인한 범위와 한계를 명시하며, 소스 조건의 증명을 실제 WASM 전체의 형식 증명으로 주장하지 않는다.
- 실행 환경, 입력 범위, 후보 탐색·시간·메모리 예산을 고정하고 반복 측정한다. 개발자가 미리 실행해 둔 캐시만으로 성공을 만들지 않는다.
- 모순된 전제, 불가능한 후조건, 미지원 표현, 탐색 예산 소진과 timeout을 구분한다. 후보를 못 찾았다는 이유로 해가 없다고 판정하지 않는다.

**완료 기준:** 세 작업 모두 선언한 환경과 예산에서 합성·증명되고, 독립적인 기대 결과와 WASM 실행 결과가 일치한다. 실패 사례는 정확히 분류되며 실행 가능한 성공 결과를 새로 생성하지 않는다. 일반화된 새 합성 기능에는 선정한 문제 외의 회귀 사례도 포함한다.

**결과물:** 실제 업무 명세, 합성·증명·실행 검증, 측정된 지원 범위와 실패 설명.

### 4. 결과를 실제 앱으로 사용한다

**목표:** 합성 결과를 일상 작업에 사용할 수 있게 한다.

- 한 프로젝트에서 입력, 검증된 계산 호출, 결과 표시, 필요한 상태 저장까지 연결한다.
- 개발 실행과 static build를 같은 명세에서 제공한다.
- 유효하지 않은 입력과 저장·runtime 오류를 화면에 표시하고 복구할 수 있게 한다.
- 깨끗한 환경에서 설치 → 프로젝트 시작 → 명세 작성 → 실행 → static build를 검증한다.
- 실제 브라우저에서 세 사용자 작업을 수행한다. Node shim이나 WASM 단독 실행은 브라우저 사용성의 근거로 대신하지 않는다.

**완료 기준:** 사용자가 별도의 계산 코드 없이 앱을 실행하고, 입력을 바꿔 결과를 얻고, 새로고침 후 필요한 상태를 복구한다. 생성된 static 결과를 개발 서버 없이 실행할 수 있다. 해당 배포 방식에 필요한 외부 서버가 있다면 의존성과 한계를 명시한다.

**결과물:** 완결된 reference app, 설치·실행 가이드, 브라우저 검증 기록.

### 5. 요구사항 변경과 실패에서 회복한다

**목표:** 처음 한 번 성공한 데서 끝나지 않고 프로그램을 유지한다.

- 기본 계산의 조건, 구간 정책, 항목 제한을 각각 변경한다.
- 명세 수정 → 재합성·증명 → 앱 반영을 끝까지 검증한다.
- 잘못된 명세에서는 오류와 기존 실행 결과의 상태를 명확히 표시한다. 이전 성공 결과가 최신 명세를 만족한다고 오해하게 만들지 않는다.
- 정상 명세로 복구하면 깨끗한 새 빌드와 동일한 결과를 얻는다.
- 저장 형식이 바뀌는 실제 변경이 있다면 이전 데이터 복구 또는 명시적 이전 절차를 검증한다.
- 사용자에게 실행 결과가 어떤 명세에서 생성됐는지와 어디까지 검증됐는지를 확인할 방법을 제공한다. 외부 데이터의 사실성은 증명 범위에 포함하지 않는다.

**완료 기준:** 세 작업의 변경·실패·복구가 모두 통과하고, 오래된 결과를 최신 검증 결과로 보여주거나 저장 데이터를 조용히 잃는 경우가 없다.

**결과물:** 변경·복구 검증 사례, 결과와 명세의 연결 정보, 필요한 데이터 이전 안내.

### 6. 외부 사용자가 끝까지 완주한다

**목표:** 내부 개발자의 시연을 다른 사람이 사용하는 제품으로 바꾼다.

- 내부 구현을 모르는 대상 사용자 두 명 이상이 깨끗한 환경에서 문서만 보고 세 작업을 수행한다. 이는 출시 판정용 최소 관찰이며 전체 시장의 사용성을 대표하는 표본은 아니다.
- reference app 복사 실행 외에, 각 사용자가 같은 지원 범위 안의 새 정책 하나를 명세로 작성하고 앱에 반영한다.
- 진행 시간, 멈춘 지점, 도움 요청, 명세 오해와 실패 복구를 기록한다.
- 막힌 부분을 고친 뒤 영향을 받은 작업을 재검증하고, 최종 전체 흐름을 다시 확인한다.
- 지원 환경에서 설치·CLI·편집기·브라우저 흐름을 확인하고, 지원 범위·숫자 의미·검증 경계·known limitations를 문서화한다.
- 최종 소스와 배포할 artifact를 연결하고, 동일 환경에서 재현 가능한 빌드와 핵심 회귀 검증을 남긴다. 공개 배포는 별도 승인 후 수행한다.

**완료 기준:** 두 사용자 모두 개발자의 명세 작성·계산 구현 도움 없이 설치, 작성, 합성, 실행, 변경, 실패 복구를 완주한다. 새 정책도 성공한다. 완료 판정에 사용한 소스·artifact와 검증 기록이 일치하고, 해결되지 않은 필수 작업은 없다.

**결과물:** 사용자 완주 기록, 지원 범위 문서, 검증된 배포 후보. 공개 여부는 완성 판정과 별도로 기록한다.

## 최종 완료 판정

다음 조건을 모두 충족하면 첫 제품을 완성으로 판정한다.

- 실제 사용자가 필요하다고 확인한 문제 하나를 해결한다.
- 핵심 계산은 사용자 명세에서 합성하며 개발자가 구현을 대신하지 않는다.
- 구현 방법을 지정하지 않은 문제의 후보 탐색과 정책 변경 후 재합성을 입증한다.
- 사용자가 부족한 명세를 발견·보완하고, 허용되는 결과가 의도와 맞는지 확인한다.
- 증명, WASM 실행, 실제 앱 결과가 동일한 계약을 따른다.
- 사용자가 새 정책을 작성하고 기존 요구를 변경할 수 있다.
- 실패를 성공으로 표시하지 않고, 수정 후 안전하게 회복한다.
- 외부 사용자가 문서만으로 전체 흐름을 완주한다.
- 지원 범위, 미지원 요구와 증명하지 않는 부분이 명확하다.

이 판정은 첫 대상으로 고정한 지원 범위에 적용한다. “어떤 프로그램이든 자동 생성한다”는 주장으로 확장하지 않는다.

## 지금 추가하지 않을 것

범용 자연어 앱 생성, 새 runtime/backend, 무제한 재귀, 동적 컬렉션 전체 증명, DB·인증 플랫폼, marketplace, plugin 생태계는 현재 필수 작업으로 잡지 않는다. 선정한 사용자 작업을 막는 구체적인 근거가 생기면 필요한 부분만 채택한다. 외부 시스템을 사용하는 앱을 선택한다면 필요한 adapter와 오류 처리는 해당 앱의 범위에 포함한다.

별도 proof 인증서·서명 시스템이나 전면적인 언어 재설계도 먼저 추진하지 않는다. 결과와 명세의 연결, 실제 배포의 무결성, 기존 의미 보존에 필요한 검증은 생략하지 않는다.

## 착수 순서와 작업 규칙

당장은 엔진이나 UI를 수정하지 않고 다음 세 작업을 순서대로 수행한다.

| 순서 | 작업 | 결과물과 완료 기준 |
| --- | --- | --- |
| 1 | 계산기 요구사항 확정 | 입력·출력·단위·범위·정책과 변경 전후 기대 결과를 기록한다. 세 사용자 작업, 관계·제약 중심 사례, 조건이 부족한 사례를 포함한다. 사용자 확인 전 요구는 가정으로 표시한다. |
| 2 | 기존 엔진 가능성 조사 | 각 요구를 최소 `.ax` 사례로 재현한다. 언어 표현, 후보 탐색, 증명, WASM 실행을 따로 확인하고 현재 가능·기존 기능 조합 가능·핵심 기능 부족·첫 범위 밖으로 분류한다. 소스·명령·옵션·결과·실패 근거를 남긴다. |
| 3 | 실제 구현 목록 작성 | 아래 판단 기준으로 필요한 변경만 선정한다. 각 항목에 사용자 작업, 수정 위치, 의존성, 예상 비용, 검증과 완료 기준을 연결하고 우선순위를 정한다. |

구현 우선순위는 P0: 핵심 합성·증명·명세 보완을 막는 문제, P1: 앱 실행·변경·복구·사용자 완주를 막는 문제, P2: 완료 기준을 막지 않는 편의 개선 순서다. 의존성이 있는 선행 작업은 먼저 수행한다. P2는 첫 완성의 필수 범위에 포함하지 않는다.

## 엔진 확장 판단 기준

사용자 작업의 실패는 엔진 확장의 자동 승인 사유가 아니다. 실패마다 다음을 순서대로 확인한다.

1. 기존 연산·계약 분해·프로젝트 연결로 해결할 수 있는가? 해결되면 재사용하되, 핵심 알고리즘이나 숨은 정답을 사용자가 대신 작성하게 만들지 않는다.
2. 원인이 핵심 합성 기능 부족인가? 명세 모순·조건 부족·미지원 표현·탐색 예산·검증·runtime 실패를 구분하고 재현한다. 입력 범위를 줄여 확인한 결과를 원래 범위의 성공으로 표시하지 않는다.
3. 세 작업 중 둘 이상에서 재사용되는가? 한 작업에서만 필요하면 대상을 조정하는 선택을 우선 검토한다. 단, 합성의 차별성을 입증하는 필수 사례라면 한 작업이어도 별도 근거로 채택할 수 있다.
4. 확장 비용에 비해 사용자 가치가 충분한가? 해결할 작업, 변경할 계층, 증명 soundness와 회귀 위험, 유지 비용, 기존 코드 방식 대비 이점을 함께 기록한다.

판정은 **기존 기능 재사용 / 제한된 실험 / 엔진 확장 / 제품 범위 조정 / 보류** 중 하나로 남긴다. 근거가 부족하면 제한된 실험에 시간·탐색·변경 범위와 중단 조건을 먼저 정한다. 종료 후 성공 가능성과 비용을 평가하고, 실패할 때마다 실험 예산을 늘리지 않는다.

엔진 확장은 핵심 완료 기준을 막고 재사용 또는 차별성 근거가 있으며, 비용과 위험을 검증 가능한 범위로 제한할 수 있을 때 채택한다. 이 조건을 만족하지 않으면 제품 범위 조정이나 보류를 제안한다. 범위 조정 시 포기하는 사용자 가치와 새 완료 기준을 명시하고 사용자에게 확인받는다. 조정 전 기준을 달성한 것처럼 기록하지 않는다.

## 진행과 판정

단계는 위 순서로 진행하되, 설치 문제나 명세 오해처럼 앞 단계의 가정이 깨지면 해당 단계로 돌아가 수정한다. 기술적으로 해결할 수 없다는 근거가 나오면 범위 변경을 제안하고, 이미 정한 성공 조건을 조용히 줄이지 않는다.

각 단계는 사용자 작업, 필요한 구현, 검증, 미해결 항목을 함께 남긴다. 새 버전 번호, 기능 개수, 테스트 총수만으로 제품 완성을 판정하지 않는다. 일정과 속도 목표는 첫 작업의 측정 후 정하며, 현재 문서에는 근거 없는 기간이나 성능 약속을 넣지 않는다.
